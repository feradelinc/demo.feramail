# Developer guide

The application has no runtime dependency on another Studio. React components are separate workspaces under `src/components`; `server/app.js` owns sessions, fixed upstreams, operation dispatch, provenance and send authorization. `shared/operations.json` is generated from exact main and qualified-runtime router snapshots with candidate OpenAPI metadata. `scripts/audit.mjs` checks their hashes, baseline/runtime registration reconciliation and candidate documentation presence. `docs/contracts/` contains the audited source references and their original source provenance; backend source remains subject to its original repository license.

The qualified source is the Email service in immutable release `v0.1.0-api-release.20261011.83`, source provenance `2f7bed5083c600932420415b456e704e1c5eb853` on `fix/preprod35-db-profile`. Main and candidate branches differ from that release. The two read helpers (`GET /api/v1/send/preflight`, `GET /api/v1/send/operations/{operationId}`) are disabled unless the operator opts into that qualified profile. Do not infer current deployment from candidate OpenAPI alone.

FerAuth current branch/commit and Render current branch/commit are pinned in inventory. The existing Render working tree contains user changes and was preserved. API-key login sends `x-api-key` only to Auth; ordinary Email requests use the returned JWT and session instance. Product and named permission denials are actual upstream responses, never bypassed by the proxy.

Credentials and pending confirmations are held in transient server memory. Cookies are HttpOnly/SameSite Strict and Secure on HTTPS. Idle and absolute session lifetimes are one hour, bounded by JWT expiration. Logout/identity changes clear client workspace caches and server credentials. Login attempts are limited to ten per client per minute; total demo requests to 240. Session/client/recipient maps have capacity bounds.

New resource names must use the random session prefix; existing unrelated UUIDs cannot be updated or deleted. New-name collisions are checked before creation. Imports are limited to real returned global sources, and new imported UUIDs are recorded. Deletes require the exact session-created UUID. Cleanup is never automatic. Losing a session does not authorize adopting old resources.

Configuration saves provide every source field and deliberately replace credentials. The backend currently overwrites missing values. Ordinary password reads are not possible. Username is redacted from traces; re-enter it when replacing existing credentials. Save is not connection verification and does not send. The persisted secure flag does not override port-derived transport.

Template saves include all editor fields to avoid destructive omission. Names are at most 60 characters and category at most 10. Search fields are JSON arrays encoded into the URL; owner is fixed to the session. Current backend model lookup ignores projection, so the actual inspector may contain more fields than requested. The separate backend correction PR addresses that discrepancy.

The browser generates the source backend's subject/body XSLT wrappers and uses XSLT 1.0. This is an inspectable approximation of the associated FeraRender path, not exact backend output. XML errors are visible. DTD/entities, external document/doc/text/collection lookups, include/import, result-document and extension constructs are denied. Preview HTML is sanitized into a script-disabled, opaque-origin sandbox with a restrictive CSP. Remote images/styles/fonts/tracking and link navigation are blocked. Only validated base64 PNG/JPEG CID images can appear inline. No preview calls `/api/v1/send`.

An optional exact preview uses only the configured and allowlisted Render origin's `POST /api/v1/xml` with `{xml,xsl}`, through an authenticated session. It is disabled by default and must be authorized independently. The response is presented as the actual Render result. Separate product access and backend serializer limitations may still produce a real failure; the Studio does not fabricate a replacement result.

Send preparation resolves the SMTP profile and selected template within the actual tenant before creating a challenge. It verifies account/recipient/SMTP policy and bounds attachments/fan-out. A send consumes its confirmation before dispatch and locks concurrent submissions. Failures are never automatically retried. Ambiguous results are recorded as uncertain; a matching retry requires explicit duplication acknowledgement plus a new recipient confirmation. Baseline sends omit optional service-delivery bindings and therefore do not claim idempotency.

Requests and responses are redacted recursively; secrets echoed in response strings are removed. Sanitized downloads contain method, URL, redacted headers, status, elapsed time and outcome, with request bodies, rendered content, recipients and attachment contents omitted. Normal inspector content remains inspectable for the user's own session. No credentials or documents are persisted in localStorage.
